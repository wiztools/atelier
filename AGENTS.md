# AGENTS.md

Guidance for AI agents working in this repository. Atelier is a **desktop AI workshop for agentic chat and image generation, local or cloud** — a macOS-first desktop app (Go + Wails v2 + React/TypeScript) that wraps a model in an agentic loop (triage → planning → tool use → final response) with per-action permission gates. Chat runs against local Ollama or cloud OpenRouter; image generation runs locally (Ollama) or via fal.ai **or Replicate** (`Models.ImageProvider`), video generation via fal.ai **or Replicate** (`Models.VideoProvider`, empty = fal), with cloud keys stored in the OS keychain.

## Commands

```sh
wails dev                          # Run frontend + Go backend together (dev server at :34115)
go test ./...                      # Run all Go tests
npm run build --prefix frontend    # Type-check + build the Vite frontend
wails build                        # Produce build/bin/Atelier.app
./bld.sh                           # One-shot: gofmt -w *.go && npm build && go test && wails build
./release.sh [--dry-run] [--skip-tests] <semver>  # Bump version, build, sign, notarize, tag (macOS)
```

`./bld.sh` runs `gofmt -w *.go` — note the glob is root-level only, so all Go source lives at the repo root in a single `package main`.

Prerequisites: Go 1.27+, Node.js, [Wails CLI v2](https://wails.io) (`go install github.com/wailsapp/wails/v2/cmd/wails@latest`), and a running Ollama.

## Repository Layout

Everything is **one flat Go package (`main`) at the repo root**. There are no subpackages. The frontend is a Vite/React app under `frontend/`.

| File | Role |

| `main.go` | Wails entry point. Embeds `frontend/dist` via `go:embed`, registers the macOS menu, and mounts a custom asset handler that serves generated image artifacts from disk under the `/atelier-artifact/` URL prefix. `augmentGUIPath` runs before anything else: a Dock/Finder launch inherits launchd's minimal PATH (no `/opt/homebrew/bin`), so without prepending the Homebrew directories a Homebrew-installed ffmpeg/whisper would look "not installed" to local-binary detection on first run. |

| `triage.go` | First-pass routing: the harness model decides `needsTools` + `responseMode` (`text`/`image`/`vision`/`video`/`audio`) + `mediaEdit` (the request is a local edit of an existing clip — screenshot/split/join/crop-resize-rotate/aspect-ratio conversion/extract/replace audio — rather than generation; the edit-tool list in `triageSystemPrompt` names the local ffmpeg tools plus the fal `reframe_video`, so an aspect-ratio conversion routes as an edit and stays tool-backed with a fal key even when no ffmpeg is installed; RESTYLING is deliberately carved out of `mediaEdit` — changing a clip's look (anime, claymation, a different character) re-renders every frame, so it routes to responseMode "video" with the fal `restyle_video` tool (tools_registry.go, default `fal-ai/kling-video/o3/pro/video-to-video/edit` behind `VideoRestyleModel`; the Settings picker is the sixth partition of fal's video-to-video category, app.go); when no ffmpeg CLI is configured the harness turns the flag into a code-authored install note for the final model plus a deterministic reply fallback, see local_ffmpeg.go — unless the turn's tools delivered a video (`turnDeliveredVideo` in harness.go), in which case both stand down: the fal video-to-video tools (upscale/reframe/restyle) run without ffmpeg, so "local video editing isn't available" would be false beside a delivered clip) + `imageEdit` (the image sibling: convert/resize/crop/rotate/flip/watermark/collage/adjust/strip-metadata of an existing image; CONTENT CHANGES are carved out the way RESTYLING is for clips — altering what an image shows (retouch a subject, change proportions, remove/add an element, switch outfit/hairstyle/art style) re-renders the image, so it routes to responseMode "image" with `generate_image` taking the attachment as its edit reference, never to text on the theory that the local tools can't do it (conv_d53a86bd51bd5740ed30e683); missing-backend note via local_images.go) before anything else runs. | `local_ffmpeg.go` | The ten local media-transform tools that run on the detected ffmpeg CLI: `screenshot_video` (frame at a timestamp → JPEG image artifact; anamorphic sources — frames stored squeezed at one size, stretched to a larger display size on playback, e.g. 960x720 storage at 4:3 sample aspect shown as 1280x720 — are resampled to the display size via `screenshotAspectCorrection` so captures aren't squeezed: ffprobe's `sample_aspect_ratio` decides, the no-ffprobe fallback compares the MP4's tkhd presentation size against `mp4CodedVideoDimensions`' stsd coded size, a 90°/270° rotation swaps the display axes, and a notice explains the resample), `contact_sheet_video` (N frames tiled into ONE montage JPEG — the storyboard-style overview a poster prompt reads from a single attachment; a failed probe or unknown codec falls back to MP3 192k), `extract_audio` (AAC→`.m4a` / MP3→`.mp3` copy when the probed codec allows, else MP3 192k with a notice), `replace_audio` (new audio under the attached video; video copied when the container is MP4-family, `-shortest`), `transform_video` (the video sibling of `transform_image`: change shape via `aspectRatio` with `mode` — the default `crop` center-crops and trims the longer side; `blur`/`pad` instead contain the full frame on a target-aspect canvas, filling the added area with an enlarged blurred copy (`fillFilterChain`: `split` → cover-scale+`gblur` → centered `overlay`) or black bars (`scale`+`pad`), canvas dims from `aspectFillDimensions` keeping the source's long edge (1920×1080 → 9:16 lands on the standard 1080×1920 vertical frame); the fal `reframe_video` tool (tools_registry.go, default `fal-ai/ltx-2.3/reframe` behind `VideoReframeModel`, per-second-of-input billing via the rendered clip's own duration) is the generative counterpart that outpaints the added area — `width`+`height` land on exactly those pixels via the cover idiom `scale=W:H:force_original_aspect_ratio=increase,crop=W:H` — never stretched, one alone preserves aspect — plus `rotate`/`flip` and a `speed` playback multiplier (0.25–8; `setpts` on the `-vf` chain plus `atempoChain`'s pitch-preserving tempo stages, each inside atempo's [0.5, 2] envelope, on `-af`). Alone, `speed` rescales the whole clip; with the optional `start`/`end` portion bounds it runs ONE `filter_complex` (`videoPortionSpeedFilterComplex` → `ffmpegPortionSpeedArgs`): the normal-speed head and tail `trim` around a rescaled middle, concatenated — geometry ops apply after the concat, so shape covers the whole output, and an end at/past the clip's end clamps open with a notice. The bounds resolve against the clip's duration via `transformVideoPortionFacts` (ffprobe, else the MP4 sniff — `mp4DurationSeconds` plus `mp4HasAudioTrack`, which also gates the `[0:a]` chains since referencing audio on a silent clip is a filtergraph error); an aspect crop needs the source's dimensions, resolved by ffprobe with the MP4 `tkhd` read (`mp4VideoDimensions`, so generation outputs work without ffprobe) as fallback; everything re-encodes H.264 CRF 18 with even-dimension flooring), and `probe_media` (ffprobe facts as evidence — offered only when ffprobe resolves; `ToolProbeResult` also carries the aspect anomaly: `sampleAspectRatio`/`displayAspectRatio`, the computed display size when pixels aren't square, display-matrix `rotation`, and the audio side's `sampleRate`/`channels`). Sources are the turn's media slots (attachment/mention/history-fallback) decoded to staged temp files; outputs ride `ToolVideoResult`/`ToolAudioResult`/`ToolImageResult` so artifacts, carry-forward (an extracted track feeds a later transcribe_audio; a split clip feeds a later screenshot; a split audio part or joined recording feeds transcribe_audio the same way), and the media-usage ledger all work unchanged — the activity's `Provider:"ffmpeg"` is pre-filled so the engine layer doesn't mis-attribute them to fal. These tools make multi-kind turns reachable (a screenshot plus an extracted track in one turn), so the harness persists any media-kind combination via `appendChatAssistantTurnWithTurnMedia`. Their `at`/`start`/`end`/`mode` call params ride `HarnessToolCall` and are declared in `harnessToolPlanSchema` so the format-schema planner can emit them (transform_video reuses the image-side geometry params `aspectRatio`/`width`/`height`/`rotate`/`flip`, already declared there, plus its own float `speed` and the shared per-tool `mode` selector; its portion bounds reuse split_video's `start`/`end`). | `video_poster.go` | Poster frames for video artifacts: WKWebView paints a `<video>` black until playback, so every persisted clip — generated (fal/Replicate/local ffmpeg outputs, all through `writeChatMediaArtifacts`'s `contentType == "video"` gate) and user-attached (`historyContentForMessage`'s video loop) — gets a still frame written beside it as a `<stem>_poster.jpg` sibling (`vid_<hex>.mp4` → `vid_<hex>_poster.jpg`). ## Architecture & Control Flow

A chat turn flows through `App.StreamChat` → `HarnessEngine.RunChatStream`:

1. **Start** — persist the user turn to history, assign a `conversationID`.
2. **Triage** (`triage.go`) — the *harness model* decides `{needsTools, responseMode, toolTask, reason}` with a structured-output JSON schema. A response that doesn't decode gets one correction retry with the parse error fed back (`triageMaxAttempts`, the planner's invalid-plan repair idiom; conv_b8581c45e97098773e5bd238 — a model that answered in prose instead of routing); provider errors are not retried. Failures still **fail safe** to the tool path (`needsTools=true`, `responseMode="text"`) — a wrong fallback costs latency, never correctness — and the fail-safe path skips skill selection (`TriageFailed` on `harnessTurnContext` → `triageFailedSkillSkipReason`): selection is another weak-model JSON judgment, and trusting the model that just failed a simpler one compounds the failure (there: failed triage → knowledged skill match → planner invoked `kc` → spurious permission prompt). The planner itself still runs on the fail-safe path — filesystem and media tools are deterministic capabilities. `triageChatTurn` records its own "triage" steps, one per attempt, like `selectSkillForTurn`. An unreachable harness *provider* (e.g. OpenRouter with no key) is a config error, not a model failure: `harnessProviderUnavailable` reports it before triage rather than burning the turn on the fail-safe rails.
3. **Planning loop** (`prepareChatTurnLoop`) — only when tools are needed. Up to `harnessChatMaxSteps` (3) rounds, bounded by `harnessChatMaxWallTime` (2 min), at most 3 tool calls per round. The planner emits a JSON plan validated against the tool schema; invalid plans are fed back to the planner as corrections rather than aborting.
4. **Tool execution** (`ToolGateway`) — read-only tools run unattended; `write`/`exec` tools require UI approval via `atelier:tool-permission` events (2-minute timeout, fail-closed). The turn's media slots come from `resolveTurnMedia` (`harness.go`): explicit media — this turn's attachments plus `@`-mentioned assets — first, with the history fallback gated across kinds. A bare follow-up ("animate it", "extend the clip") backfills only the newest image-or-video artifact, and an image+video pair — the motion-control combination in `generate_video`'s mode table — is never half-assembled from fallback (conv_150c5923a5c31be0cda40397: a stale model-generated video silently flipped "Animate the image" to motion control). Audio sits outside the gate; it keeps the per-kind latest-wins fallback. The planner's counterweight is `generate_video`'s `source` param (`"image"`/`"video"`/`"motion"`): it names the media the user's words point at when the slots imply another, drops the other side with a notice, and re-reads the named kind from conversation history when the slots lack it — an unfulfillable source fails the call rather than generating the wrong clip. `useVideoAs:"reference"` outranks `source`.
5. **Final response** — a *different* model (the primary/chat model) streams the user-facing answer. It receives tool observations as **evidence**, never as instructions, and is told (via code-authored notes in the message stream — see `toolEvidenceNote`/`toolEvidenceSystemNote` in `harness.go`) what actually ran and what failed so it cannot claim success that didn't happen.

### Self-update flow (updater.go + updater_darwin.go)

`main.version` (ldflags-injected by release.sh) is the single version source; the running app never reads its own Info.plist. Checks fetch GitHub's stable redirect URL (`releases/latest/download/update-manifest.json`, attached to every release by release.sh alongside a zip of the stapled app) — at most once per 24h (persisted in `~/.atelier/updates/state.json`, written only on successful fetch so transient failures retry) plus a same-period ticker for always-open sessions; `version == "dev"` skips the automatic path so `wails dev` never nags. An available update raises `atelier:update-available` (banner + Settings status); `InstallUpdate` is gated on `len(a.streams) == 0` (the frontend queues a click made mid-turn), runs download → SHA256 → `codesign --verify` → plist-version-match → Team-ID pin, then hands off to the detached `install.sh` helper and quits via the `updaterQuitting` flag, which bypasses the `beforeClose` confirmation. The helper preserves its log as `~/.atelier/updates/last-update.log` **before** relaunching — the new instance's startup staging sweep would otherwise race it away.

### Critical design invariants (don't break these)

- **Planner output is telemetry, never prompt text.** The primary model's system prompt is never mutated per-turn — no tool-evidence notes, no `toolTask`, nothing. Code-authored notes (`toolEvidenceSystemNote`, etc., via `toolEvidenceNote`) ride in the **message stream** (prepended to the tool-evidence user message, or a trailing user message when no tools ran), so message #0 stays byte-identical across tooled and un-tooled turns and the prefix cache survives. A brief/reason from a weaker harness model must not cap what the primary model is allowed to know.
- **Tool evidence is delivered as `role:"tool"` messages to the planner** (so it re-plans on evidence), but as a **single `role:"user"` message to the final model** (`toolEvidenceUserMessage`). This is deliberate: the primary model isn't doing native tool-calling, and some providers (Mistral via OpenRouter) reject a bare `tool` role after a `user` role.
- **`role:"tool"` is the harness's canonical evidence shape; adapters translate it.** The OpenAI wire format only accepts a tool message when the preceding assistant message carries `tool_calls`, which the format-schema planner never emits. Ollama is lenient; OpenRouter returns `400 tool message has no preceding assistant tool_calls`. `openRouterMessages` rewrites unbacked tool messages into a `role:"user"` observation (shared `toolObservationsPrefix`). Keep this in the **adapter**, not the harness — the harness must not learn which providers are strict.
- **`num_ctx` is sent explicitly on every call** (`defaultOllamaNumCtx = 16384`, selectable in Settings → Providers). History is trimmed to fit (`truncateChatHistory`) and planner-round tool evidence is bounded by a num_ctx-derived budget (`plannerEvidenceBudgetChars` → `buildToolResultMessages` compacts the largest results, with the truncation marked) rather than letting Ollama silently truncate from the front — front truncation drops the planner's instructions, and the harness panel flags any step whose prompt still overflowed; the oldest dropped message gets a `[Earlier conversation was omitted...]` marker.
- **Image base64 never enters model context.** Generated images are stripped from tool-result messages before they reach any model; the harness extracts them separately for the UI and history.
- **An image-generation model cannot produce text/vision.** `responseModelFor` falls back to the harness model for image captions, and `responseProviderFor` falls back to that model's provider. Both take the resolved `harnessTarget` rather than reading config: an unset harness model resolves to the *primary* model on the *primary* provider, so a raw `Models.HarnessProvider` read would pair that model with the wrong endpoint.
- **The harness model runs on either provider.** `resolveHarnessTarget` returns model and provider as one `harnessTarget`; never resolve them separately. All three harness calls — triage, skill selection (`selectSkillForTurn`), and planning — go through `completeWithHarnessModel`, never `ollamaClient` directly. `supportsNativeTools` is Ollama-only capability detection, so a non-Ollama harness plans via the format schema.
- **Harness model defaults to the primary model *and* its provider** when unset — a one-model setup must still work, including a cloud-only one with no local Ollama.
- **The workspace root is per-conversation and immutable.** Each conversation pins a `ConfigFilesystemTool.Root` at creation (`HistoryConversation.Workspace`); turn 2+ reads it from the record and ignores `ChatRequest.Workspace`. The single override point is `resolveTurnWorkspace`, called in `StreamChat`/`writeChatConversation` *before* `newHarnessEngine` — it rewrites `config.Tools.Filesystem.Root`, and because the tool registry is cached per-`HarnessEngine` (`toolRegistry()` via `registryOnce`) with each stream building a fresh engine, that one override scopes the registry descriptions, the filesystem layer, and the harness/triage prompts through `h.config`. Do **not** refactor the root out of `workspaceRootPhrase` or the prompt templates — the override makes that unnecessary. Legacy SchemaVersion 1 records are backfilled to the default in `loadForAppend`/`readConversationWorkspace`. The command allowlist stays global; the global `Tools.Filesystem.Root` is the default for new conversations and the fallback for the manual tool methods.
- **Per-conversation model overrides ride the same seam.** `HistoryConversation.ModelOverrides` (`*ConversationModelOverrides`, nil = none; no schema bump — absent reads as inherit) pins the Settings → Models selections plus the primary chat model for one conversation, **differentially**: empty fields inherit the live global Settings, so later global changes still reach unpinned fields. `applyConversationModelOverrides` runs in `StreamChat`/`writeChatConversation` immediately after `resolveTurnWorkspace`, overlaying pinned fields onto the per-stream config copy *before* `newHarnessEngine` — one rewrite scopes harness routing (`resolveHarnessTarget`), tool-registry gating, per-tool default models, and gateway routing through `h.config`; a primary override also rewrites `req.Provider`/`Model`/`SelectedModel` so the override beats whatever the request carries (workspace semantics). The overridden config is never persisted. Turn 2+ reads the override from the record; turn 1 has none yet, so `ChatRequest.ModelOverrides` carries the override for the conversation being created — applied to the first turn's config and pinned onto the record by `requestModelOverrides` in both creation paths (the workspace/project lifecycle; ignored for existing conversations). `SetConversationModelOverrides` is the one sanctioned rewrite of the field after creation (refused while streaming, all-empty clears to nil). Frontend: the Settings → Models tab and the per-conversation screen render the same extracted `ModelSelectionPanel` (`App.tsx`) — the conversation variant adds a Primary section and marks pinned fields with a reset chip; every other field (generation defaults, whisper binary included) renders identically in both variants (the panel's per-model duration options follow the *draft's* video models there). While a primary override is pinned, the composer's picker edits the override instead of global config (the record's while a conversation is open, the pending `draftModelOverrides` while composing the first message of a new one).
- **`HistoryConversation.ProjectID` follows the workspace lifecycle.** Pinned at creation from `ChatRequest.ProjectId` (validated by `resolveTurnProject` — an unknown project fails the turn before anything persists), immutable turn 2+, with `MoveConversationToProject` as the only sanctioned rewrite. A conversation's project reaches `@`-mention resolution through the record (or the `fallbackProjectID` on the turn-1 build path, where the record isn't on disk yet): `resolveReferencedAssets` resolves conversation-locally first and only then widens to the library. Cross-conversation mentions persist on the citing turn with an **absolute `HistoryContent.Path`** — every reader (`hydrateHistoryContent`, the `read*ArtifactAsDataURL` helpers via `contentArtifactPath`) resolves absolute paths as-is. The `resolveTurnMedia` history *fallback* stays conversation-local; only explicit mentions reach across. Hard-deleting a project/library removes member conversation dirs (deletes are refused while any member streams via `App.streamConversations`).
- **Every provider call is a step; every step transition is live.** Each model call (triage, skill, planning, model_call/streaming) records a `HarnessStep` with provider, model, prompt+completion tokens, and a `HarnessRequestSnapshot` (hashes/sizes only — raw prompts are never persisted). `HarnessRun.onUpdate` fires on every `appendStep`/`completeStep`/`complete` and emits the full run snapshot as the `atelier:harness-run` Wails event; the frontend renders these directly and never fabricates in-flight state. `TestHarnessTelemetryCoversEveryModelCall` (in `harness_telemetry_test.go`) pins the convention: one step per intercepted provider HTTP call. Conversation title generation (`generateConversationTitle`, the non-streaming path) is the one sanctioned exception — it runs after the turn and is not part of the run.
- **Token usage lives on model-call steps only.** Bookkeeping steps (`queued`, `saved`, `evaluation`, `tool_call`) carry no token counts — the turn total rides in `providerResponse.tokens` — so summing steps counts each model call exactly once. The frontend's per-model usage fold (`summarizeModelUsage`) filters to `triage`/`skill`/`planning`/`model_call`/`streaming`; keep that set and the Go recording sites in sync.
- **Dollar cost rides the same ledgers as usage, in USD millionths (`CostMicros`).** Two sources, both fail-soft-zero: OpenRouter's server-billed `usage.cost` (parsed in `openrouter_client.go`/`openrouter_provider.go` into `TokenUsage`/`ChatCompletionResult`, recorded on the model-call steps beside the token counts), and fal media generation estimated at the tool gateway from fal's pricing API (`fal_pricing.go`: `GET api.fal.ai/v1/models/pricing`, batched over `configuredFalEndpointIDs`, 24h TTL cache on `App.falPricing` with a 10-minute negative TTL; the quote's `unit` picks the billing quantity — image count, requested or rendered seconds, characters (a bare count, or a block like "1000 characters" for elevenlabs/f5-tts), one request, a block of video tokens, a megapixel of generated pixels, or fal's generic per-output "units" (seedream v5 bills one per image, gemini-omni edit one per clip — conv_26ef0c4f generated a seedream edit with no dollar row until that unit was taught; flat per-audio "audios" prices the same way) — from `falBillingHints`, so a per-second model with no computable duration estimates nothing rather than guessing; "compute seconds" and "minutes" stay unpriced because the request can never state them). Token-billed video models (seedance-2.x, quoted per "1000 tokens") report no usage in fal's response, so the gateway computes the count from fal's documented formula — `tokens = height × width × seconds × 24 / 1024` — over the effective resolution tier (explicit, else the schema's default via `schemaStringInput`) and the rendered clip's own duration (`mp4DurationSeconds` parses moov/mvhd from the downloaded bytes, the only source when duration was "auto"); video-source turns add the source clips' own durations — fal's formula bills `input_video_duration + output_duration` — parsed from the staged data URLs BEFORE `resolveMediaURL` hosts them (`falVideoSourceSeconds`, captured in the gateway's fal GenerateVideo path), and any clip that won't parse skips the estimate rather than billing the parsed half (conv_859908bf: a seedance-2.5 reference-to-video extension over a 2.25s clip reported $0.000067 — text only — until this capture existed), while per-second models on video-source turns still read `req.Duration` (the billed extension length) because the rendered clip embeds the source footage; the seedance reference-to-video pages also multiply the price by 0.6 whenever video inputs ride (`falVideoReferenceDiscount`, gated to the `bytedance/seedance-2.` family via `falBillingHints.PriceMultiplier`, applied in `estimateFalCostMicros` after quantity × unit price). Megapixel-billed models (the ltx-2.3-22b family, quoted per "megapixel of generated video data", `width × height × frames` — conv_801b5619 extended a clip with no dollar row until this unit was taught) read the frame size from the rendered clip's own tkhd (`mp4VideoDimensions`; "auto" video_size inherits the source clip's size, so the output is the only source) and the frames from the container's stts sample count for pure turns (`mp4VideoFrameCount`, exact) or the schema's `num_frames` default (`schemaNumberDefault`) for video-source turns — the same don't-probe-the-embedded-source principle as seconds; MP-billed image models sum their decoded payloads' dimensions (`imageResultMegapixels` over `imagePixelDimensions`, a magic-byte sniffer for PNG/JPEG/GIF/WebP — no codec dependency, and non-data-URL references contribute nothing). The turn total is **derived from the run** (`harnessRunCostMicros`, summing step + activity costs) inside `buildChatAssistantTurn` and the media-turn persistence path (`appendChatAssistantTurnWithMedia`) into `providerResponse.costMicros`, never threaded through the streaming result — the run is the ledger everything renders from, and failed turns keep their burned cost. Ollama/openai-compatible report no cost; local media tools carry none. **Replicate reports no cost at all** (no pricing API, nothing on the prediction), so its media activities carry `HarnessToolActivity.CostUnknown` instead — stamped at the `toolActivityFromResult` attribution site when the provider is "replicate" and a media kind was produced, and for "fal" media activities that priced to zero (the fal estimate is fail-soft: pricing cache miss, a billing unit the request can't state, source durations never locally readable) so an unpriceable paid call never reads as free — and the frontend renders "?" in the row's cost slot plus a "~"-prefixed total (the sum covers only reported costs), never `$0.00`. Frontend rows with no cost and no unknown flag show nothing in the cost slot, never `$0.00`.
- **Media consumption is recorded as activity fields, never token rows.** Media models (fal/Replicate video, fal audio, any-backend image) burn no tokens, so their consumption rides `HarnessToolActivity.Provider`/`Model`/`MediaKind`/`MediaCount`, populated in `defaultHarnessToolActivity`'s type switch from the tool's own result payload — the resolved model after defaulting, not the planner's `Call.Model`. `Provider` (backend attribution: "fal"/"replicate"/"ollama"/"openai-compatible") is filled one layer up in `toolActivityFromResult`, because video generation and the video transforms (upscale/reframe/restyle) route by `config.Models.VideoProvider` (`videoGenerationProvider`) while audio stays fal-only, while `generate_image` routes by `config.Models.ImageProvider` — the same fields the tool gateway reads — which the per-tool activity builders don't receive. The activity's `CostMicros` (fal pricing estimate) is stamped by the gateway onto the `Generated*`/`ollamaGenerateResponse` payload after a successful call and copied through the same type switch; `ToolTranscribeResult` joins with cost but no `MediaKind`, and the frontend media fold admits cost-carrying activities without counts so its rows reconcile with the turn's money total. The frontend's media fold (`summarizeRunMediaUsage`) reads `tool_call` activities only and renders a sibling "media generation" block, never a row in the token table; failed calls carry no payload and drop out. Turns saved before these fields existed (e.g. conv_a27d6008) fall back to the `providerResponse.tool` block via `mediaUsageFromToolSummary` — per turn, run activities take precedence so nothing is double-counted, and the legacy provider is derived best-effort (fal for video/audio, `fal-ai/` prefix for images).
- **Failed turns persist their run.** The early-return failure paths in `RunChatStream` call `saveFailedAssistantTurn` (best-effort) so an errored turn still leaves its ledger — and the tokens it really burned — in history, with the error text as the turn's content and `providerResponse.error`.
- **Internal telemetry rides `json:"-"` side channels, zipped at the recording site.** `HarnessToolResult.Permission` (`*ToolPermissionDecision`, carrying outcome approved/denied/timeout/cancelled + wait time) is invisible to planner evidence and bindings; `toolActivities` copies it onto the persisted `HarnessToolActivity` fields, the same pattern as planner `Call` params. Never deliver internal diagnostics via `Notices` — those render to the user verbatim.

## Conventions

- **Single `package main`, all files at repo root.** No internal subpackages.
- **Config is merged with defaults, never raw.** `mergeAppConfig(config)` fills every unset field from `defaultAppConfig()`. The allowlist (`defaultFilesystemToolAllowedCommands`) and the prompt's command list are read from the same `ConfigFilesystemTool.AllowedCommands`, so they cannot drift.
- **Tool params go directly on the call object, not nested under `args`.** Plan validation produces a specific error (`toolCalls[N].args must be ...; tool parameters like path go directly on the call object`) when a model nests them.
- **All user/storage paths are normalized** via `normalizeStoragePath` (`~` expansion → absolute). The filesystem tool resolves and confines every path to the configured root.
- **IDs are prefixed random hex** (`randomID("conv")`, `"run"`, `"permission"`, `"chat-" + unixnano`).
- **Settings explanatory copy lives in `InfoHint` hovers, not standing hint lines.** A description of what a feature does (capability lists, how detection works, degradation behavior) goes in the "i" icon's hover text (`InfoHint` in `frontend/src/App.tsx`) — on the section heading or the field's label row — so the Settings screen stays scannable. The visible `<span className="hint">` lines are reserved for actionable status only: a missing prerequisite with its fix ("Add a fal.ai API key above…", "No ffmpeg CLI found…: `brew install ffmpeg`") or a load error. Rule of thumb: if the sentence would still be true with everything configured and working, it belongs in a hover, not on the screen.
- **Wails bindings are generated, and must be committed in the same change.** `frontend/wailsjs/go/main/App.{js,d.ts}` mirror exported `App` methods; `frontend/wailsjs/go/models.ts` mirrors the public structs reachable from bound methods. **Any change to a bound `App` method _or_ to a field on a struct it exposes** (e.g. adding `Loop`/`Voice` to `HarnessToolCall`, `Notices` to `HarnessToolResult`) must be followed by regenerating **and committing** these files — run `wails generate module` (or `wails dev`/`wails build`, which regenerate as a side effect). A Go-only change that adds struct fields without the regenerated `models.ts` merges cleanly but leaves the frontend types stale on `main`; the frontend then can't see the new fields. Commit the bindings alongside the Go change, and discard any incidental mode-only churn the generator makes to `frontend/wailsjs/runtime/`.
- **Git commits** use conventional prefixes (`feat:`, `fix:`) in the log.

## Testing

- Standard `go test ./...`. Tests are **table-driven** and live alongside the code (`*_test.go`).
- HTTP is mocked with a `roundTripFunc` (`app_test.go`) injected into an `*http.Client` — no real Ollama/OpenRouter calls in tests.
- `fakeProvider` (`provider_test.go`) implements `ChatProvider` for harness-level tests.
- `app_test.go` is the largest test file (~4000 lines) and covers the full harness pipeline, streaming cleanup, history, tools, and config merging. Helpers like `waitForStreamCleanup` and `harnessStepByKind` exist there.
- `harness_telemetry_test.go` covers harness telemetry: token accounting (prompt + completion per model-call step), TTFT, failed-turn persistence, permission-decision recording, request snapshots, and the instrumentation-coverage rule (one step per provider call). Its `telemetryTestConfig`/`persistedHarnessRun` helpers drive a full turn against a mocked Ollama and read the run back from history.

## Gotchas

- `frontend/dist/` is embedded at compile time (`//go:embed all:frontend/dist` in `main.go`). The frontend must be built (`npm run build --prefix frontend`) before `wails build`; `wails dev` rebuilds it live.
- `version` in `main.go` is `"dev"` unless injected at link time by `release.sh` (`-ldflags "-X main.version=..."`).
- Config lives at `~/.atelier/config.json`; history/artifacts under `~/.atelier/history/`. Skills are loaded from **both** `~/.agents/skills/<name>/SKILL.md` and `~/.atelier/skills/<name>/SKILL.md`.
- The OpenRouter API key is stored in the OS keychain, **not** in config.json. An absent key returns `("", nil)`; callers treat "not configured" and "empty" uniformly.
- `go.mod` has a commented-out `replace` directive for local Wails development — uncomment only when hacking on Wails itself.
- Permission requests time out after 2 minutes and fail closed (denied) if no UI is attached.
